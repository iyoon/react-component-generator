# Create PR

현재 브랜치의 커밋과 diff를 분석해 템플릿에 맞는 PR을 만들고, **확인을 묻지 않고 바로** 생성한다.

이 스킬은 fork된 별도 컨텍스트에서 돈다. 이전 대화 내용을 볼 수 없으므로, PR에 들어갈 모든 정보는 git 이력(`git log`, `git diff`)과 인자에서 얻는다. 대화에서 들은 내용을 추측해서 채우지 않는다.

## 인자

`$ARGUMENTS`를 공백 기준으로 해석한다. 순서는 상관없다.

| 인자 | 의미 | 기본값 |
|------|------|--------|
| `ko` / `en` | 템플릿 언어 | `ko` |
| 태스크 번호 | 제목 접두사에 쓸 식별자 (예: `PROJ-123`, `proj/123`) | 브랜치 이름에서 추출 |
| `--draft` | draft PR로 생성 | 일반 PR |
| `--base <브랜치>` | PR 대상 브랜치 | 저장소 기본 브랜치 |
| `--no-push` | push 생략 (이미 push된 경우) | 필요하면 push |

## 템플릿

언어에 맞는 파일을 읽어 구조를 그대로 따른다. 이 파일들이 PR 본문 형식의 기준이다.

- 한국어: `references/template.ko.md`
- 영어: `references/template.en.md`

## 절차

### 1. 사전 확인
```bash
git branch --show-current
gh repo view --json defaultBranchRef --jq .defaultBranchRef.name
git status --short
```
- 현재 브랜치가 base(기본 브랜치)와 같으면 중단하고 "작업 브랜치에서 실행하세요"라고 알린다. base에 직접 PR을 만들 수 없기 때문이다.
- 커밋되지 않은 변경이 있으면 PR에 포함되지 않는다는 점을 최종 보고에 적는다. 대신 커밋해 주지는 않는다 (커밋은 `commit` 스킬의 역할).
- 이미 이 브랜치의 열린 PR이 있는지 확인한다: `gh pr view --json url,state`. 있으면 새로 만들지 않고 그 URL을 알린다.

### 2. 변경사항 분석
```bash
git log --oneline <base>..HEAD
git diff <base>...HEAD --stat
git diff <base>...HEAD
```
- base는 `--base` 값, 없으면 저장소 기본 브랜치다. 원격 기준이 필요하면 `origin/<base>`를 쓴다.
- 커밋이 0개면 중단하고 알린다.
- diff를 실제로 읽는다. 커밋 메시지만 보고 쓰면 실제 변경과 어긋난다.
- `.env`, 키, 토큰 같은 민감정보가 diff에 보이면 PR 생성을 중단하고 파일 위치만 알린다. 값은 출력하지 않는다.

### 3. 제목 작성
형식: `[태스크번호] 요약`

- 태스크 번호는 인자에서 먼저 찾고, 없으면 브랜치 이름에서 `<코드>/<숫자>` 또는 `<코드>-<숫자>` 패턴을 찾아 쓴다.
- 어느 쪽에서도 못 찾으면 접두사 없이 `요약`만 쓰고, 최종 보고에 "태스크 번호를 찾지 못해 접두사를 생략했다"고 적는다. 번호를 지어내지 않는다.
- 요약은 템플릿 언어와 맞춘다. 한국어는 50자 내외, 영어는 70자 이내로 명령형 현재 시제, 마침표 없이 쓴다.
- 이 저장소의 커밋 컨벤션(`feat`/`fix`/`refactor`/`chore`)을 요약 앞에 붙이지 않는다. 접두사는 태스크 번호가 대신한다.

### 4. 본문 작성
템플릿의 섹션을 모두 채운다. 섹션을 지우거나 순서를 바꾸지 않는다. 리뷰어가 PR마다 같은 위치에서 같은 정보를 찾을 수 있어야 하기 때문이다.

- **개요/배경**: 왜 필요한지를 쓴다. 무엇을 했는지가 아니라 동기다. 커밋 이력에서 드러나지 않으면 변경의 성격만 간결히 쓴다.
- **변경 사항**: 파일 단위가 아니라 동작 단위로 요약한다. 커밋 순서가 아니라 리뷰어가 이해하기 좋은 순서로 쓴다.
- **테스트 방법**: 실제로 근거가 있는 것만 쓴다. 변경된 테스트 파일, 프로젝트의 테스트 명령어(`AGENTS.md`, `package.json`)를 바탕으로 재현 방법을 적는다. 실행해서 확인하지 않은 결과를 통과했다고 쓰지 않는다. 확인하지 못했으면 "미실행"이라고 쓴다.
- **리뷰어 참고사항**: 트레이드오프, 알려진 한계, 리뷰어가 특히 봐줬으면 하는 부분. 없으면 "없음".
- **Breaking change / 배포 영향**: 하위 호환성, 마이그레이션, 환경변수·설정 변경, 배포 순서. diff에서 근거를 찾아 쓰고, 없으면 "없음".

### 5. push와 PR 생성
```bash
git push -u origin HEAD          # --no-push 이면 생략, 이미 push됐으면 불필요
gh pr create --base <base> --title "<제목>" --body-file <임시 본문 파일> [--draft]
```
- 본문은 여러 줄이므로 `--body-file`로 넘긴다. 임시 파일은 scratchpad 디렉토리에 만든다.
- push는 실패하면 원인을 보고하고 멈춘다. `--force`는 쓰지 않는다.

### 6. 보고
생성된 PR URL, 사용한 제목, base 브랜치, 템플릿 언어를 알린다. 건너뛴 항목(태스크 번호 생략, 미커밋 변경, 미실행 테스트 등)이 있으면 함께 적는다.

## 주의
- fork된 컨텍스트라 호출한 쪽에는 최종 보고만 전달된다. URL과 건너뛴 항목을 보고에 반드시 담는다.
- PR 본문에 API 키, 토큰, 내부 URL 같은 민감정보를 넣지 않는다.
- PR을 수정·닫기·머지하지 않는다. 생성만 한다.
