# Commit

변경사항을 분석해 논리적 단위로 나누고, 컨벤션에 맞는 한국어 커밋 메시지를 작성한 뒤 **별도 승인을 묻지 않고 바로** 커밋한다. 커밋은 로컬에서 되돌릴 수 있고, 사용자가 커밋을 요청한 것 자체가 승인이기 때문이다.

## 커밋 컨벤션

형식: `<type>(<scope>): <한국어 요약>` (scope는 선택)

| type | 용도 |
|------|------|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 빌드·설정·의존성·스킬 등 기타 작업 |

- 요약은 한국어, 50자 내외, 마침표 없이 작성한다.
- 필요하면 빈 줄 뒤에 본문(무엇을/왜)을 덧붙인다.
- 예: `feat: Google 모델 실패 시 자동 폴백 추가`, `chore(skills): agents-md 스킬 최신화`

## 절차

### 1. 변경사항 분석
```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 확인
```
- 변경 내용을 실제로 읽고 파악한다. 파일명만 보고 판단하지 않는다.
- untracked 파일은 내용을 확인한다.
- `.env`, 키·토큰·비밀번호 등 민감정보가 포함된 파일이 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 하나의 목적만 담는다 (기능 / 버그 수정 / 리팩터링 / 설정을 섞지 않는다).
- 각 단위에 포함될 파일 목록과 type을 정한다.
- 한 파일에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`로 분리하는 방안을 제안한다.
- 변경이 하나의 목적이면 커밋 1개로 충분하다.

### 3. 커밋 메시지 작성
- 단위별로 위 컨벤션에 맞는 한국어 메시지를 작성한다.
- 변경의 "무엇"보다 "왜/효과"가 드러나게 쓴다.

### 4. 바로 커밋
승인을 기다리지 않고 단위별로 순서대로 커밋한다.

- 단위별로 해당 파일만 `git add <파일>` 후 `git commit`한다 (`git add -A`, `git add .` 지양).
- 커밋 후 `git log --oneline -n <커밋 수>`와 `git status`로 결과를 확인하고, 아래 형식으로 보고한다.

```
커밋 1: feat: 컴포넌트 생성 API 에러 처리 추가
  - src/api/generate.ts
  - src/lib/errors.ts

커밋 2: chore: 스킬 설정 갱신
  - skills-lock.json
```

- 사용자가 "먼저 보여줘", "계획만 알려줘"처럼 확인을 요청한 경우에만 커밋 계획을 보여주고 승인을 받은 뒤 진행한다.
- 잘못 나눈 커밋은 사용자가 요청하면 `git reset --soft HEAD~N`으로 되돌려 다시 커밋한다.

## 주의
- push는 하지 않는다. 사용자가 요청한 경우에만 수행한다.
- `--no-verify`, `--amend`, force 옵션은 사용자가 명시적으로 요청하지 않으면 사용하지 않는다.
- pre-commit hook이 실패하면 원인을 수정하고 **새 커밋**으로 다시 시도한다.
- 커밋할 변경사항이 없으면 그 사실만 알리고 종료한다.
